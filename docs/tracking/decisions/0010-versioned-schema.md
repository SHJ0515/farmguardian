# 빈 DB 기준선과 순차 SQL로 스키마를 관리한다

## 배경과 결정

기존 데이터 복원과 Refresh 저장 방식 전환을 함께 다뤄야 했으며, 자동 스키마 수정만으로 변경 순서와 복구 영향을 확인할 수 없었다.

확인된 빈 DB에 V1→V2를 적용하는 Flyway 흐름을 사용한다. 이미 적용한 파일은 변경하지 않는다. 자동 baseline·clean·out-of-order를 막고 Hibernate는 validate로 매핑을 확인한다. 공통 Flyway 기본값은 false이며 관리 대상과 다음 버전 적용을 확인한 경우에만 활성화한다.

## 대안과 결과

- 데이터가 있는 DB에 자동 baseline을 붙이면 실제 상태와 기준선 일치가 확인되지 않으므로 채택하지 않았다.
- Hibernate update/create를 스키마 변경 수단으로 병행하면 순차 SQL의 변경 의미가 달라지므로 사용하지 않는다.
- V2는 옛 Refresh 테이블을 제거한다. 코드 버전만 되돌리는 복구는 충분하지 않으며 현재 DB에 맞는 별도 백업이 필요하다.
- H2 create-drop 테스트는 SQL 제약조건·실제 MySQL 잠금 검증을 대신하지 않는다. DDL 계정과 애플리케이션 CRUD 계정의 분리는 아직 완료되지 않았다.
