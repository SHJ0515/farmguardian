# 미해결 문제

사진·알림·촬영 경로의 소유권 검증 공백은 소스 대조로 확인했다. 실제 계정을 대상으로 한 공격 재현·외부 발송·DB 변경 시험은 수행하지 않았다.

## 사진 접근과 과거 소유권

- 조건: 로그인 사용자가 타인의 사진 ID 또는 장치 ID로 조회한다. 상세·장치별 목록은 principal을 받지 않고 ID만 조회한다. 장치 A→B 재할당 뒤 전체 목록도 현재 장치 소유자를 따라간다.
- 영향: 사진 URL·분석·좌표의 교차 노출과 과거 사진의 잘못된 귀속.
- 지금 해결하지 못하는 이유: query·schema·API 테스트 변경과 기존 사진 owner 근거·격리 정책 결정이 필요하다.
- 접근: 생성 시점 소유권과 owner 조건 조회를 설계하고, 타인 접근·연결 해제·재할당·소유자 불명 행을 회귀 검증한다.

## 촬영 요청자가 넣은 사용자 ID 신뢰

- 조건: 유효 Access를 가진 사용자가 path에 다른 소유자의 userId·deviceId를 넣는다. 서비스는 두 path 값과 장치 소유자의 관계만 검사하고 principal을 비교하지 않는다.
- 영향: 타인의 장치에 촬영 명령을 발행할 수 있는 경로가 남는다.
- 지금 해결하지 못하는 이유: Controller/Service와 앱 URL 계약 변경이 필요하다.
- 접근: principal에서 사용자 ID를 얻고 path userId를 제거한다. 타 사용자 요청은 gateway 호출 전에 거부되는지 검증한다.

## FCM 토큰의 소유권과 로그

- 조건: 토큰 문자열만 알면 인증 사용자 누구나 삭제할 수 있다. 이미 다른 계정에 등록된 토큰은 신규 등록 시 변경 없이 무시한다. 삭제·전송 실패 로그는 원문 토큰을 남긴다. 탈퇴해도 토큰이 남는다.
- 영향: 알림 주소 삭제·잘못된 수신 계정 유지·토큰 노출·탈퇴 후 발송 위험.
- 지금 해결하지 못하는 이유: 소유권 코드·로그 수정과 계정 전환/탈퇴 정책 결정이 필요하다.
- 접근: 호출자 조건 조회·삭제와 원문 제거를 우선하고, 이전/거부·동시 등록·탈퇴 처리 테스트를 정한다. 관리자 개별 알림의 기존 응답 유지 결정과 토큰 보안 개선을 혼동하지 않는다.

## 물리·가상 장치 경계와 등록 경쟁

- 조건: 직접 촬영용 장치를 일반 API로 해제한 뒤 다른 계정이 예측 가능한 UUID로 연결할 수 있다. 물리 장치 등록에는 보유 증명·경쟁 잠금이 없고 `CONNECTED`만 거부하므로 `INACTIVE`도 연결 경로를 통과한다.
- 영향: 가상 장치와 사진의 소유권 오염, 동시 등록 충돌, 비활성 상태의 의미 상실.
- 지금 해결하지 못하는 이유: 종류 필드·등록 방식·비활성 전이·탈퇴 lifecycle·동시성 정책이 미정이며 코드/DB 변경이 필요하다.
- 접근: 공급 장치만 등록한다는 범위를 지키고 물리 장치와 MOBILE을 분리한다. 시리얼/UUID를 비밀 인증값으로 취급하지 않는다.

## 해충 판정 불일치와 실패 상태 부재

- 조건: 저장 응답의 `total=1`이지만 신뢰도 항목은 모두 0.2 미만이다. 분석 응답은 해충 없음, 상세는 해충 있음으로 계산한다. 결과 JSON이 없거나 잘못되면 상세는 false다.
- 영향: 같은 사진에 대한 화면·알림 불일치, 분석 실패를 해충 없음으로 오인.
- 지금 해결하지 못하는 이유: 신뢰도 상향의 정확한 경계와 상태·표시 계약을 정한 뒤 코드/테스트를 변경해야 한다.
- 접근: 0.8 수준 상향과 함께 판정의 공통 의미·분석 상태·누락/오류 표시를 정의한다. 푸시 실패 후 결과 보존과 분석 실패 후 사진 보존을 함께 검증한다.

## 입력과 외부 응답 경계

- 조건: 모바일 분석에 외부 임의 URL이나 양수가 아닌 크기를 보낼 수 있고, 별도의 객체 소유권·저장소 허용 목록 검증이 없다. FastAPI null/비정상 필드도 충분히 검사하지 않는다. 온도·습도 입력은 저장되지 않는다.
- 영향: 외부 분석기에 원치 않는 URL 전달, 잘못된 데이터·예상 밖 오류, 소비자가 기대한 센서 정보 유실.
- 지금 해결하지 못하는 이유: 저장소 계약·값의 상한·센서 데이터 활용 여부가 미정이고 입력/외부 응답 테스트가 필요하다.
- 접근: 실제 연동 저장소와 입력 의미를 먼저 정하고 외부 호출 전 거부 사례를 만든다. 상한이나 센서 보존 규칙을 추측하지 않는다.

## Access 폐기와 탈퇴 후 데이터

- 조건: 탈퇴·로그아웃 뒤 만료 전 Access를 사용하면 JWT 필터는 현재 계정 상태를 조회하지 않는다. 탈퇴 이메일은 조회에서 숨겨져도 DB UNIQUE 값은 남는다.
- 영향: Refresh 폐기와 Access 사용 가능 기간의 차이, 재가입·보존 데이터 처리의 불명확성.
- 지금 해결하지 못하는 이유: Access 잔여 수명·이메일 재사용·연관 데이터 보존이 사용자 보류/미정이다.
- 접근: 즉시 폐기 또는 잔여 수명 허용을 명시적으로 선택하고 탈퇴·역할 변경·이메일 재사용 경계 테스트를 설계한다. 로그인 실패 응답 통일도 별도 보류다.

## 재현·성능 검증과 계약 검증 공백

- 조건: 현재 기본 테스트는 H2/mock 중심이고, 사진 업무 전용 테스트·고정 부하 데이터·부하 스크립트·전체 AsciiDoc 소스가 없다. 사진 Slice JSON도 자체 고정 envelope 검증이 없다.
- 영향: 전체 기능 재현이나 성능 개선 효과, 소비자의 메타데이터 파싱을 일관되게 입증하기 어렵다.
- 지금 해결하지 못하는 이유: 문서 작업을 넘어 도구·시험 데이터·앱/장치/분석기 구성을 선택하고 테스트를 작성해야 한다.
- 접근: 로컬 기능 흐름과 부하 시나리오를 구분해 재현하고 같은 조건의 기준선·개선본을 비교한다. 새 측정 전 처리량·SLO를 확정하지 않는다.

## 과거 안내의 불일치

- 조건: README에는 옛 Refresh 테이블·공개 API 설명과 이미 구현된 기능의 미완료 목록이 남아 있다. 과거 roadmap은 실제 운영 배포를 최종 목표로 삼는다.
- 영향: 다음 작업이 완료된 기능을 다시 만들거나 현재 포트폴리오 범위 밖 운영 준비를 강제할 수 있다.
- 지금 해결하지 못하는 이유: 사용자가 기존 기록 보존을 승인했으며 이번 정리는 새 기준 문서 생성과 진입 지침 재구성으로 한정했다.
- 접근: 실제 사용 안내를 갱신하는 별도 작업에서 README를 수정한다. 과거 날짜별 증적은 당시 기록으로 보존하며 새로운 운영 승인으로 읽지 않는다.
