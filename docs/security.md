# 보안 정책

보호 대상은 계정·비밀번호, 인증 토큰과 로그인 세션, 장치 제어권·위치, 사진 URL·분석 결과, 앱 알림 토큰이다. 로컬 포트폴리오에서도 타 사용자 접근과 비밀값 노출을 정상 동작으로 취급하지 않는다. 현재 URL 접근 제한과 자원별 소유권 검증의 완성도는 서로 다르다.

## 인증과 실패 경로

1. 가입은 일반 사용자 역할로만 허용하고 비밀번호를 BCrypt로 저장한다. 관리자 역할을 가입 입력에서 받지 않는다. 이메일 중복은 거부한다. 이메일 인증·비밀번호 강도·시도 제한은 미구현이다.
2. 로그인은 계정과 비밀번호를 확인한다. 같은 사용자·클라이언트의 기존 활성 Refresh 세션을 폐기하고 새 세션을 만든다. 다른 클라이언트의 세션까지 폐기하지 않는다. 계정 없음과 비밀번호 불일치의 응답 통일은 사용자 보류 상태다.
3. 일반 요청의 Bearer는 Access만 허용한다. 서명·issuer·audience·용도·필수 claim·시각·역할이 맞지 않거나 만료되면 인증을 만들지 않는다. Refresh를 Bearer로 보내도 사용자 권한을 얻지 못한다.
4. 공개 요청은 잘못된 Access 헤더만으로 일괄 차단하지 않는다. 가입·로그인 입력과 재발급 본문의 Refresh는 각 업무에서 계속 검증한다.
5. 재발급은 Access 없이도 호출할 수 있지만, 유효한 Refresh와 일치하는 사용자·클라이언트·토큰 이력·활성 세션이 필요하다. 과거 토큰 재사용을 탐지하면 해당 세션을 폐기하고 실패시킨다. 폐기 기록은 실패 응답 때문에 취소되어서는 안 된다.
6. 로그아웃은 인증 주체와 Refresh 소유자·클라이언트가 같은 현재 세션만 폐기한다. 탈퇴는 해당 사용자의 모든 활성 Refresh 세션을 폐기한다.

기발급 Access는 현재 사용자 DB 상태를 매 요청 조회하지 않는다. 로그아웃·탈퇴·역할 변경·Refresh 재사용 탐지 후 Access를 즉시 무효화할지, 남은 유효기간을 허용할지는 미정이다. Refresh 폐기만으로 Access 즉시 폐기가 구현됐다고 설명하지 않는다.

## 주체별 접근 범위

| 주체 | 행위 | 허용 조건과 금지 범위 |
| --- | --- | --- |
| 익명 | 서버 안내·가입·로그인·재발급 | 지정된 네 개의 정확한 method/path만 진입 가능; 재발급 성공에는 Refresh 검증 필요 |
| USER 또는 ADMIN Access | 자기 장치 조회·연결·수정·해제 | 사용자 ID는 인증 주체에서 얻으며 다른 소유자의 장치를 조작하지 않음; 등록 증명과 경쟁 제어는 미완료 |
| USER 또는 ADMIN Access | 자기 사진 분석·조회 | URL 인증은 적용됨; 사진별 조회와 과거 소유권 보호는 아직 불완전 |
| USER 또는 ADMIN Access | 자기 FCM 토큰 등록·삭제 | 자기 토큰만 다루는 것이 목표; 삭제의 소유권 검사와 계정 전환 정책은 미완료 |
| USER 또는 ADMIN Access | 자기 장치 촬영 | URL 인증은 적용됨; 현재 path 사용자 ID를 신뢰하는 결함이 있어 인증 주체 기준으로 변경 필요 |
| ADMIN | 관리자 장치 조회·개별 알림 | 전용 API 이관 예정. 현재 모든 관리자 경로와 구 직접 발송·AVAILABLE 목록 경로는 차단됨 |
| DEVICE | 공급 장치의 IoT 분석 | 사용자 JWT와 분리된 장치 인증이 필요. 현재 전용 인증이 없어 IoT 분석 경로 차단 중 |
| 모든 주체 | 전체 알림·중복 사용자 안내·미정의 경로 | 현재 차단. 역할이 ADMIN이어도 기본 거부를 우회하지 못함 |
| 내부 오류 처리 | `/error` | ERROR 디스패치와 `/error`가 동시에 맞을 때만 허용; 외부 직접 호출·다른 ERROR 경로는 예외 아님 |

네이티브 앱은 직접 HTTP와 `Authorization: Bearer`를 사용한다. 쿠키·브라우저·WebView 인증은 채택하지 않았다. 이 전제로 CSRF를 비활성화했으며, 무상태 세션 설정 자체를 CSRF 안전성의 근거로 삼지 않는다. HEAD·OPTIONS·Actuator를 일괄 공개하지 않고, 웹 클라이언트나 상태 점검이 필요해지면 노출 경계를 다시 정한다.

## 관리자 이관 시 적용할 확정 정책

- 최초 관리자는 수동 지정한다. 앱/API에 역할 승격·강등 기능을 만드는 결정은 없다.
- 매 관리자 요청마다 **JWT ADMIN AND 현재 DB ADMIN AND 미탈퇴**를 확인한다. DB 조회 실패·계정 없음은 허용으로 처리하지 않는다. 일반 사용자 API 전체에 이 검사를 확대하는 결정은 아니다.
- 관리자는 일반 사용자 API에서 타인의 장치·사진·알림 토큰을 우회 조회할 권한이 없다. 별도 관리 기능이 필요하면 그 행위의 정책을 먼저 정한다.
- 장치 목록은 연결 가능한 장치만, 20개 고정·ID 오름차순으로 제공한다. 앱의 장치 등록 증명을 관리자 목록으로 대체하지 않는다.
- 개별 알림은 기존 필수 제목·본문과 선택 데이터 필드를 유지한다. 추가 업무 검증·발송 제한·중복 제거는 도입하지 않기로 했으며, 재요청은 재발송이다. 새 자동 재시도·큐 도입 결정은 아니다.
- 새 관리자 감사 방식과 보존 기간은 보류다. 전체 알림의 개방도 별도 보류이며, 개별 알림 정책을 전체 알림에 대한 승인으로 확대하지 않는다.

## 자격증명 관리

| 종류 | 생성·저장·사용 | 만료·폐기·교체 |
| --- | --- | --- |
| Access JWT | HS256, 사용자 ID·역할·이메일·용도·issuer·audience·jti·발급/만료 시각 | 공개 설정 기본 30분; 환경변수로 변경 가능. 개별 Access 즉시 폐기는 미정 |
| Refresh JWT | 권한 claim 없이 발급; DB에는 SHA-256 해시와 jti·세션·시각·상태만 저장 | 기본 7일, 성공할 때 교체; 재사용·로그아웃·탈퇴 시 세션 폐기. 만료 이력 정리 주기는 미정 |
| JWT 서명 키 | 로컬은 별도 ignored override; 운영진이 공급한 실제 비밀값을 소스·테스트에 복사하지 않음 | 키 교체 시 기존 토큰도 검증 실패. 현재 다중 키 전환은 없음 |
| MySQL·MQTT | 외부 설정으로 주입; DB 덤프·브로커 비밀번호를 문서에 넣지 않음 | 신규 계정 검증 후 구 계정 폐기. 실제 공급자 측 교체 완료 증거는 없음 |
| Firebase | 명시 활성화 시 ADC 또는 JAR 외부 서비스 계정 파일 | 새 identity의 시험 발송 검증 후 구 키 폐기. 저장소에서 파일을 지운 것만으로 교체 완료가 아님 |
| FCM·장치 자격증명 | FCM은 앱 전달용 주소이며 사용자 인증 수단이 아님. 장치 UUID도 인증 비밀이 아님 | FCM 소유자 변경·무효 토큰 정리, 장치 credential 발급·회전·폐기는 미정/미구현 |

실제 비밀번호·JWT·Refresh/FCM 토큰·서비스 계정 키·Authorization 헤더를 저장소와 일반 로그에 노출하지 않는다. 공개된 합성 테스트 fixture는 실제 자격증명과 구분한다. 현재 FCM 삭제·실패 로그에는 토큰 원문이 남는 결함이 있다. 서명된 사진 URL과 좌표도 사용자 데이터이므로 무조건 공개 로그에 추가하지 않는다.

## 감사 범위와 남은 결정

후속 감사 설계의 대상은 로그인 실패, Refresh 재사용·폐기, 장치 등록·연결 해제·credential 변경, 소유권 거부, 촬영 명령, 알림 발송이다. 현재 Refresh DB 이력과 애플리케이션 로그가 있다는 사실은 이 사건 전체의 감사 저장·검색·접근 통제가 완성됐다는 뜻이 아니다. 저장 위치·보존 기간·조회 권한·마스킹·관리자 발송 기록은 미정이다.

사진 소유권 보강, 장치 보유 증명, FCM 계정 전환, 로그인 실패 통일, Access 폐기, 입력 상한·URL 허용 목록·요청량 제한은 아직 완료되지 않았다. 포트폴리오 시연에서도 이 한계를 명시하고, 보안 미완료를 실제 서비스 공개 승인으로 해석하지 않는다.
